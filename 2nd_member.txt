A. DATABASE SCHEMA ARCHITECTURE & MIGRATIONS
   - Design and maintain the full relational schema across all 13 core tables.
   - Enforce primary keys (UUIDs), foreign key relations, cascade/restrict rules, and indexes.
   - Enforce data constraints (e.g., CHECK stock_quantity >= 0, non-negative prices).
   - Write and version-control all Prisma/Drizzle migrations.
   - Provide a realistic seed script (`prisma/seed.ts`) to populate dummy shops, users,
     categories, and products for team testing.

B. AUTHENTICATION & SESSION MANAGEMENT
   - `POST /api/v1/auth/register`:
     * Receives shop details (shop_name, gstin, address) + owner credentials (email, password).
     * Hashes password using bcrypt (salt rounds = 10-12).
     * Atomically creates the `tenants` record and the initial `users` record with role `Owner`.
     * Generates a signed JWT containing `{ userId, tenantId, role }`.
     * Returns the token and sanitized user/shop object.
   - `POST /api/v1/auth/login`:
     * Validates email & password against stored hash.
     * Issues signed JWT with standard expiration (e.g., 24h or 7d).
   - `GET /api/v1/me`:
     * Returns currently authenticated user details, role, and shop profile.

C. ROLE-BASED ACCESS CONTROL (RBAC)
   - Implement RBAC middleware:
     * Roles: `Owner`, `Admin`, `Cashier`.
     * Owner/Admin: Full access to pricing, reports, profit/loss, staff management.
     * Cashier: Billing (POS), stock viewing, customer lookup; restricted from modifying
       product cost prices or accessing overall profit/loss analytics.

D. MULTI-TENANCY & ROW-LEVEL SECURITY (RLS) ENGINE (CRITICAL)
   - Implement the Shared Database + Shared Schema ("Pool") Multi-Tenancy model.
   - Enable PostgreSQL Row-Level Security on all tenant-scoped tables:
     `ALTER TABLE <table_name> ENABLE ROW LEVEL SECURITY;`
     `CREATE POLICY tenant_isolation ON <table_name> FOR ALL USING (tenant_id = current_setting('app.current_tenant')::uuid);`
   - Build Express/Fastify Middleware:
     1. Intercept incoming HTTP request.
     2. Extract Bearer token from `Authorization` header.
     3. Verify JWT cryptographically using `JWT_SECRET`.
     4. Extract `tenant_id` from token payload. (NEVER read tenant_id from request body/query!).
     5. Before running queries in a request or transaction, execute:
        `SET LOCAL app.current_tenant = '<tenant_id>';`
     6. Connection Pool Safety: Ensure `app.current_tenant` is scoped to the transaction (`SET LOCAL`)
        or explicitly reset before returning the connection to the connection pool, preventing
        identity bleeding across subsequent HTTP requests.

E. MASTER DATA & CATALOG APIS (CO-OWNED / INITIALIZED)
   - Category Management:
     * `GET    /api/v1/categories` (List categories for the shop)
     * `POST   /api/v1/categories` (Add category)
     * `PUT    /api/v1/categories/:id` (Update category)
     * `DELETE /api/v1/categories/:id` (Remove category)
   - Product Catalog:
     * `GET    /api/v1/products` (List catalog with prices, SKU, attributes)
     * `POST   /api/v1/products` (Create product)
     * `PUT    /api/v1/products/:id` (Update price/details)
     * `DELETE /api/v1/products/:id` (Soft delete / deactivate)
   - Inventory Query:

F. AZURE CLOUD DATABASE PROVISIONING

4. COMPLETE DATABASE SCHEMA SPECIFICATION (OWNED BY MEMBER 2)
--------------------------------------------------------------------------------

All tables below must be defined in your Prisma/SQL migration:

1. `tenants` (Shops)
   - `tenant_id`: UUID (Primary Key, default uuid_generate_v4())
   - `shop_name`: VARCHAR(255) NOT NULL
   - `gstin_number`: VARCHAR(15) NULL
   - `address`: TEXT NULL
   - `subscription_tier`: VARCHAR(50) DEFAULT 'FREE'
   - `created_at`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

2. `users` (Staff / Owners)
   - `user_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `email`: VARCHAR(255) UNIQUE NOT NULL
   - `password_hash`: VARCHAR(255) NOT NULL
   - `role`: VARCHAR(50) NOT NULL DEFAULT 'Cashier' -- ('Owner', 'Admin', 'Cashier')
   - `created_at`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

3. `categories`
   - `category_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `name`: VARCHAR(100) NOT NULL

4. `products`
   - `product_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `category_id`: UUID (Foreign Key -> categories.category_id, NULLABLE)
   - `name`: VARCHAR(255) NOT NULL
   - `sku`: VARCHAR(100) NULL
   - `selling_price`: NUMERIC(12, 2) NOT NULL
   - `cost_price`: NUMERIC(12, 2) NOT NULL
   - `attributes`: JSONB DEFAULT '{}'
   - `is_active`: BOOLEAN DEFAULT TRUE
   - `created_at`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

5. `inventory`
   - `inventory_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `product_id`: UUID (Foreign Key -> products.product_id, UNIQUE, NOT NULL)
   - `stock_quantity`: INT NOT NULL DEFAULT 0 CHECK (stock_quantity >= 0)
   - `last_restocked_date`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

6. `customers`
   - `customer_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `name`: VARCHAR(255) NOT NULL
   - `phone`: VARCHAR(20) NOT NULL
   - `credit_balance`: NUMERIC(12, 2) DEFAULT 0.00 -- Outstanding udhaar owed to shop

7. `suppliers`
   - `supplier_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `name`: VARCHAR(255) NOT NULL
   - `phone`: VARCHAR(20) NULL
   - `payable_balance`: NUMERIC(12, 2) DEFAULT 0.00 -- Amount shop owes to distributor

8. `sales`
   - `sale_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `customer_id`: UUID (Foreign Key -> customers.customer_id, NULLABLE)
   - `total_amount`: NUMERIC(12, 2) NOT NULL
   - `tax_amount`: NUMERIC(12, 2) DEFAULT 0.00
   - `payment_method`: VARCHAR(50) NOT NULL -- ('CASH', 'UPI', 'CREDIT')
   - `sale_date`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

9. `sale_items`
   - `sale_item_id`: UUID (Primary Key)
   - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
   - `sale_id`: UUID (Foreign Key -> sales.sale_id ON DELETE CASCADE, NOT NULL)
   - `product_id`: UUID (Foreign Key -> products.product_id, NOT NULL)
   - `quantity`: INT NOT NULL CHECK (quantity > 0)
   - `unit_price`: NUMERIC(12, 2) NOT NULL
   - `line_total`: NUMERIC(12, 2) NOT NULL

10. `purchases`
    - `purchase_id`: UUID (Primary Key)
    - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
    - `supplier_id`: UUID (Foreign Key -> suppliers.supplier_id, NULLABLE)
    - `total_amount`: NUMERIC(12, 2) NOT NULL
    - `purchase_date`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

11. `purchase_items`
    - `purchase_item_id`: UUID (Primary Key)
    - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
    - `purchase_id`: UUID (Foreign Key -> purchases.purchase_id ON DELETE CASCADE, NOT NULL)
    - `product_id`: UUID (Foreign Key -> products.product_id, NOT NULL)
    - `quantity`: INT NOT NULL CHECK (quantity > 0)
    - `unit_cost`: NUMERIC(12, 2) NOT NULL
    - `line_total`: NUMERIC(12, 2) NOT NULL

12. `expenses`
    - `expense_id`: UUID (Primary Key)
    - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
    - `amount`: NUMERIC(12, 2) NOT NULL
    - `category`: VARCHAR(100) NOT NULL -- Rent, Electricity, Salaries, Transport, etc.
    - `description`: TEXT NULL
    - `expense_date`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

13. `transactions` (Unified Double-Entry Ledger)
    - `transaction_id`: UUID (Primary Key)
    - `tenant_id`: UUID (Foreign Key -> tenants.tenant_id, NOT NULL)
    - `entity_type`: VARCHAR(50) NOT NULL -- ('CUSTOMER', 'SUPPLIER')
    - `entity_id`: UUID NOT NULL
    - `amount`: NUMERIC(12, 2) NOT NULL -- Positive for credit, Negative for debit
    - `reference_type`: VARCHAR(50) NOT NULL -- ('SALE', 'PURCHASE', 'PAYMENT')
    - `reference_id`: UUID NOT NULL
    - `created_at`: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

CRITICAL INDEXES TO CREATE:
- B-Tree composite index on `(tenant_id, product_id)` in products and inventory.
- B-Tree composite index on `(tenant_id, sale_date)` in sales.
- B-Tree composite index on `(tenant_id, created_at)` in transactions.

  -- Create Tenant Isolation Policy

8. CLOUD COMPUTING VIVA / EXAM TALKING POINTS FOR MEMBER 2
--------------------------------------------------------------------------------

When professors or evaluators ask you about your work:

Q1: "How do you achieve multi-tenancy?"
Answer: "We implemented the Pool Model (Shared Database, Shared Schema) where all shops
share tables partitioned by a tenant_id column. To avoid the infamous 'leaky tenant'
risk of application-level bugs, we enforce isolation at the database kernel level using
PostgreSQL Row-Level Security (RLS). Every request cryptographically sets a session variable
`app.current_tenant` from a verified JWT, meaning the database itself physically forbids
reading or writing any row that doesn't match the current tenant."

Q2: "Why PostgreSQL over MongoDB or MySQL?"
Answer: "Financial applications require strict ACID compliance, relational foreign keys,
and double-entry balance correctness. PostgreSQL was specifically chosen because it provides
native, robust Row-Level Security (RLS) policies at the kernel level, and supports JSONB
for flexible product metadata without breaking relational constraints."

Q3: "How do you handle connection pooling with RLS?"
Answer: "Because Node.js reuses database connections via a pool, setting a session variable
globally could leak identity to another shop on the next request. We solve this by executing
`SET LOCAL app.current_tenant = ...` strictly within a database transaction boundary,
which PostgreSQL automatically discards the moment the transaction commits or rolls back,
guaranteeing zero cross-tenant contamination."

Q4: "How is user authentication managed?"
Answer: "We use stateless JSON Web Tokens (JWT). Passwords are never stored in plaintext—they
are hashed using bcrypt with salt rounds. The JWT encapsulates the authenticated user's ID,
assigned role (Owner/Admin/Cashier), and their verified tenant_id. The client never passes
tenant_id in request bodies; the backend extracts it exclusively from the cryptographically
signed JWT."
